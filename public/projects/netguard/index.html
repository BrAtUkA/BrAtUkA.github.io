What it does

NetGuard reads the packets going in and out of a computer, groups them into flows (one conversation between two addresses), and decides for each flow whether it looks like an attack. When it does, an alert appears on a live dashboard within about 50 milliseconds, with the type of attack, how sure the model is, and the matching technique from MITRE ATT&CK, the standard catalogue of attacker behaviour.

Three layers

A single model has blind spots. It only knows the attacks it was trained on, and it sees one flow at a time. So NetGuard stacks three detectors, each covering a gap in the others.

  • Known attacks. A fast XGBoost model first decides “benign or attack”. Flows it flags go to a second, calibrated model that names the attack: DoS, DDoS, brute force, port scan, web attack, botnet or infiltration. Calibrated means a 90 percent confidence really is right about 90 percent of the time.
  • Things it has never seen. Benign-looking flows are compared with clusters of normal traffic. Anything far from all of them is flagged as an anomaly, which is how a new kind of attack can still show up.
  • Patterns. Some attacks look innocent one flow at a time: a slow scan, a flood from many addresses, password spraying across accounts. Rules running over rolling time windows in MongoDB look for those.

Thresholds live next to the models, so making NetGuard more or less sensitive is a config change, not a code change.

The dashboard

The React dashboard has four views. Live Monitor shows the alert feed, traffic rates and charts. Clicking an alert opens everything the model saw: its confidence, the score for every class, the MITRE technique and the flow’s statistics. You can mark it confirmed or a false positive, and that feedback is stored.

Forensics answers “what else did this address do?”. Search an IP and it joins every flow and alert from that address into one timeline, using a MongoDB $lookup.

Under the hood

  • Capture can’t crash the app. Packet capture runs in its own process. If it fails, the API and the dashboard keep running.
  • Alerts are pushed, not polled. MongoDB change streams feed a FastAPI WebSocket, which is how an alert reaches the screen in about 50 ms.
  • It had to pass gates to ship. The production model learned from CICIDS2017, CIC-IDS2018 and normal traffic recorded on a home network. Before it replaced the previous one, it had to clear set targets for accuracy, false alarms on home traffic, port-scan and DDoS recall, speed and calibration.
  • Ready after install. The trained models ship with the repository, so live capture works without downloading the datasets.
